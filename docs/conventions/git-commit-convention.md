# Git 커밋 전략

## 1. 목적

이 문서는 커밋 기록만으로 변경 목적과 영향 범위, 관련 GitLab Issue를 이해할 수 있도록 커밋 메시지와 커밋 단위를 정의한다.

## 2. 기본 형식

```text
<type>(<scope>): <summary>

<body>

<footer>
```

`body`와 `footer`는 필요한 경우에만 작성한다.

```text
feat(user): 이메일 로그인 API 구현

로그인 실패 사유를 클라이언트가 구분할 수 있도록
인증 실패 응답 코드를 세분화한다.

Refs #456
```

## 3. Type

| Type | 용도 |
| --- | --- |
| `feat` | 사용자에게 제공되는 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 코드 구조 개선 |
| `test` | 테스트 추가 또는 수정 |
| `docs` | 문서 변경 |
| `style` | 포맷, 공백, 이름 정리 등 동작과 무관한 변경 |
| `perf` | 성능 개선 |
| `build` | 빌드 도구와 의존성 변경 |
| `ci` | GitLab 또는 Jenkins 자동화 변경 |
| `chore` | 위 분류에 포함되지 않는 유지보수 작업 |
| `revert` | 이전 변경 되돌리기 |

## 4. Scope

기능 변경에는 비즈니스 도메인을 사용한다.

```text
user
lesson
review
braille
```

비즈니스 도메인으로 표현하기 어려운 변경에는 다음과 같은 공통 scope를 사용할 수 있다.

```text
infra
ci
docs
deps
```

서비스 이름보다 변경 목적을 우선한다. 예를 들어 web과 backend를 함께 수정한 로그인 기능은 두 서비스명을 나열하지 않고 `user`를 사용한다.

## 5. Summary 작성 규칙

- 한글 작성을 기본으로 하되 기술 고유명사는 원래 표기를 유지한다.
- 무엇을 했는지 명확하게 작성한다.
- 문장 끝에 마침표를 붙이지 않는다.
- `수정`, `추가`, `분리`, `제거`처럼 일관된 표현을 사용한다.
- `작업`, `변경`, `업데이트`처럼 내용이 드러나지 않는 표현만 사용하지 않는다.
- 헤더는 가능한 한 한 줄, 72자 이내로 작성한다.

```text
# 올바른 예
feat(user): 소셜 로그인 실패 안내 추가
fix(lesson): 빈 문제 목록에서 발생하는 예외 수정
refactor(review): 복습 우선순위 계산 로직 분리
ci(infra): backend 이미지 빌드 단계 추가
docs(git): 브랜치 전략 문서화

# 사용하지 않음
feat: 기능 추가
fix(user): 버그 수정함.
chore: 작업
update login
```

## 6. Body와 Footer

### Body

제목만으로 설명하기 어려울 때 변경 이유와 중요한 제약을 작성한다. 코드 내용을 그대로 반복하기보다 왜 이 변경이 필요한지 기록한다.

```text
fix(user): 중복 로그인 시 이전 세션 종료

동일 계정의 동시 수업 참여를 막기 위해 새 로그인 성공 후
이미 발급된 refresh token을 만료시킨다.

Refs #462
```

### Footer

일반 작업은 관련 이슈를 다음처럼 연결한다.

```text
Refs #456
```

이슈가 없는 작업은 이슈 footer를 생략한다.

호환되지 않는 API나 데이터 형식 변경에는 다음 footer를 추가한다.

```text
BREAKING CHANGE: 로그인 응답의 token 필드를 accessToken으로 변경
```

개별 커밋에는 `Closes #456`보다 `Refs #456`을 사용한다. GitLab 기본 브랜치가 `main`이므로 `dev`를 대상으로 한 MR이나 커밋은 즉시 이슈를 자동 종료하지 않는다.

- `dev` 병합을 완료 기준으로 삼는 이슈는 MR 확인 후 수동으로 종료한다.
- `main` 대상 릴리스 MR에서는 릴리스 이슈에 `Closes #<issue>`를 사용할 수 있다.
- MR 설명에는 테스트 결과와 영향 범위를 명시하고, 관련 이슈가 있으면 함께 연결한다.

## 7. 커밋 단위

하나의 커밋에는 하나의 논리적 변경만 포함한다.

- 기능 구현과 무관한 대규모 포맷 변경을 섞지 않는다.
- 리팩터링과 동작 변경은 가능한 한 별도 커밋으로 나눈다.
- 코드와 해당 테스트는 같은 커밋에 포함할 수 있다.
- 비밀값, 빌드 결과, 개인 IDE 설정은 커밋하지 않는다.
- 임시 디버그 코드와 불필요한 로그를 제거한 뒤 커밋한다.

```text
# 하나의 MR 안에서 가능한 커밋 예시
refactor(user): 인증 응답 생성 로직 분리
feat(user): 로그인 실패 응답 코드 추가
test(user): 로그인 실패 시나리오 테스트 추가
```

MR에서 squash할 때는 위 커밋들을 최종 목적에 맞는 하나의 메시지로 정리한다.

```text
feat(user): 로그인 실패 원인별 응답 구현

Refs #456
```

## 8. 브랜치 유형별 Squash 규칙

| 병합 흐름 | Squash | 이유 |
| --- | :---: | --- |
| 하위 작업 → 상위 기능 | 사용 | 하위 작업당 하나의 커밋 유지 |
| 단일 작업 → `dev` | 사용 | 기능 단위로 기록 정리 |
| 상위 기능 → `dev` | 사용하지 않음 | 여러 하위 작업의 커밋 보존 |
| `dev` → `release/*` | 사용하지 않음 | 릴리스 대상 이력 보존 |
| `release/*` → `main` | 사용하지 않음 | 검증한 커밋과 릴리스 이력 보존 |
| `hotfix/*` → `main` | 사용 | 긴급 수정 단위를 명확히 유지 |

GitLab이 자동 생성하는 merge commit 메시지는 이 문서의 수동 커밋 형식 적용 대상에서 제외한다.

## 9. 커밋 전 확인 목록

- 변경 파일이 해당 작업 범위에 포함되는가?
- 민감 정보나 환경 파일이 포함되지 않았는가?
- 빌드 결과와 임시 파일이 제외되었는가?
- 테스트가 필요한 변경에 테스트가 포함되었는가?
- type과 scope가 실제 변경 목적을 표현하는가?
- 관련 이슈가 있으면 `Refs #<issue>`로 연결했는가?
- 커밋 메시지만 읽어도 변경 내용을 이해할 수 있는가?
