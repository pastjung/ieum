## 1. 적용 규칙

MVP는 스마트폰을 독립적으로 사용하는 저시력 시각장애인을 대상으로 모바일 학습·촉지·전문가 실시간 수업·개인화 반복 학습을 제공한다. 본 문서의 F 번호는 문서 추적용이며 API 경로나 DB 식별자가 아니다. 기능 포함 승인과 요청·응답·저장 구조 승인을 구분한다.

역할은 LEARNER / INSTRUCTOR / ADMIN 중 하나다. 검수 담당을 별도 역할로 만들지 않는다. 공개 가입은 LEARNER만 가능하고 INSTRUCTOR·ADMIN은 통제된 Seed/운영 절차로 발급한다. 관리자 공개 API·화면과 ADMIN의 강사/문제 자동 권한은 MVP에서 제외한다.

### 2.1 계정·비밀번호·로그인 제한을 두는 이유

`username`은 로그인 식별자, `email`은 인증·복구 주소로 역할을 분리한다. 두 값은 정규화 후 DB UNIQUE와 백엔드 검증을 함께 적용해 기기나 요청 경로가 달라도 같은 계정이 중복 생성되지 않게 한다. 공개 가입을 LEARNER로 고정하는 이유는 클라이언트가 role을 조작해 INSTRUCTOR·ADMIN 권한을 얻는 것을 막기 위해서다.

비밀번호는 Argon2id로 해시한다. 신규 시스템에서 메모리 사용량을 포함한 느린 해시를 적용하면 DB가 유출되더라도 대량 추측 비용을 높일 수 있기 때문이다. 최소 설정은 메모리 19MiB·반복 2·병렬도 1이며 실제 배포 서버에서 응답성과 동시 부하를 측정해 이보다 낮추지 않는 범위에서 조정한다. `password_hash VARCHAR(255)`에는 알고리즘·salt·설정을 포함한 인코딩 결과만 저장하고 원문은 저장·로그하지 않는다. [OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

MFA가 없는 MVP 비밀번호는 15~64자로 하고 유니코드·공백·붙여넣기·자동완성을 허용한다. 문자 종류 조합을 강제하지 않고 흔하거나 유출된 비밀번호를 차단한다. 이는 사용자가 예측 가능한 규칙 변형을 반복하게 하는 대신 긴 암호 문구를 사용할 수 있게 하고, 저시력 사용자의 불필요한 입력 부담을 줄이기 위한 선택이다. 비밀번호 표시 전환도 제공하되 사용자가 제출하기 전에만 확인할 수 있게 한다. [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html)

연속 로그인 실패 5회 뒤 10분 제한은 온라인 무차별 대입을 늦추면서 영구 잠금으로 정상 사용자가 계정을 잃지 않게 하는 MVP 기준이다. 성공하면 실패 횟수와 제한 시각을 초기화한다. 계정 없음·비밀번호 오류·잠김·탈퇴는 같은 실패 응답과 유사한 처리 시간을 사용해 외부에서 가입 여부를 추측하지 못하게 한다. 프론트 검증은 입력 안내와 즉시 피드백을 위한 보조 수단이며 우회 가능하므로 정규화·비밀번호·역할·잠금·토큰 검증의 최종 책임은 백엔드에 둔다. [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

Access Token을 짧은 15분 JWT로 두고 Refresh JWT의 상태를 Redis에 14일·회전 방식으로 별도 저장하는 이유는 매 요청의 인증 비용과 유출 피해 범위를 함께 제한하기 위해서다. Refresh 원문 대신 해시·jti·family와 사용 상태를 Redis에 저장해야 로그아웃·재설정·탈퇴 시 폐기하고 이전 토큰의 재사용을 탐지할 수 있다. 웹은 Secure·HttpOnly 쿠키, 모바일은 운영체제 보안 저장소를 사용해 스크립트·일반 앱 저장 영역의 노출을 줄인다. [RFC 9700 Refresh Token Protection](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)

이메일 인증·복구 JWT도 원문이 아니라 해시·jti·용도·사용 상태를 Redis에 저장하고 단일 사용·만료를 적용한다. 인증 24시간은 가입 완료 기회를 제공하고, 더 민감한 비밀번호 복구는 30분으로 제한한다. 요청 응답으로 계정 존재를 구분하지 않는 이유는 이메일 목록을 수집하는 계정 열거 공격을 막기 위해서다. [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

### 2.2 계정 공개 API·클라이언트 동작

계정 기능은 `/api/v1`의 명사형 HTTP 리소스 10개로 제공한다. 가입·내 정보·탈퇴, 로그인·Access 갱신·로그아웃, 이메일 인증 요청/완료, 비밀번호 재설정 요청/완료를 구분한다. 가입은 username·email·password만 받아 LEARNER를 만들고 인증 메일을 보낸다. 인증 전에는 토큰을 발급하지 않는다. 사용자 응답은 userId·username·email·role·emailVerified·level·createdAt을 포함하며 level은 자가 진단 전 학습자와 INSTRUCTOR·ADMIN에서 null, 진단 후 학습자에서 열린 최고 L1~L6이다. 접근성 설정·일반 프로필·역할 변경은 포함하지 않는다.

로그인·갱신·로그아웃 요청은 `X-Client-Platform`으로 WEB/MOBILE 전달 방식을 명시한다. 이 값은 권한 판단에 사용하지 않는다. WEB Refresh Token은 `__Host-refreshToken` Secure·HttpOnly·SameSite=Strict 쿠키, MOBILE Refresh Token은 응답/body와 운영체제 보안 저장소를 사용한다. `Origin` 헤더가 있는 요청의 `MOBILE` 주장은 허용 목록과 무관하게 거부하고, 허용 Origin 검사는 CORS에서 별도로 수행한다. 프론트는 Access Token을 가능한 한 메모리에 두고 동시 갱신을 single-flight로 합치며 엄격한 회전 뒤 구 Refresh Token을 재사용하지 않는다.

형식이 유효한 이메일 인증·비밀번호 재설정 요청은 계정을 조회하지 않고 `mail_outbox` 작업을 접수하며, INSERT commit 성공이 확정되면 `202`와 빈 body를, INSERT 또는 commit이 실패하거나 commit 결과가 불확실하면 `503 AUTH_STATE_UNAVAILABLE`을 반환한다. `202`와 `503`의 차이는 저장소 결과에만 따르고 계정 존재·상태·발송 적격 여부에 따르지 않으므로 계정 열거를 막는다. `202`는 내구적 작업 접수만 뜻하고 실제 메일 발송이나 편지함 도달을 뜻하지 않는다. 원문 action token은 링크의 프론트 화면/deep link·fragment에서 받아 POST body로만 백엔드에 전달한다. 비밀번호 재설정은 `users.auth_version`을 증가시켜 기존 Access와 Refresh를 모두 무효화하고 자동 로그인하지 않는다. 탈퇴는 currentPassword를 다시 확인하고 즉시 가명화·인증 폐기하며, 남은 Access Token은 보호 API의 status·auth_version 재검증으로 차단한다.

클라이언트는 오류 code를 임의 문자열 비교가 아니라 고정 계약으로 처리한다. 로그인 실패 원인은 `INVALID_CREDENTIALS`, Refresh 실패 원인은 `INVALID_REFRESH_TOKEN`, action token 실패 원인은 `ACTION_TOKEN_INVALID`로 일반화한다. API 전문과 상태 코드는 [API 명세 V2 3절](./api-spec.md#3-계정인증-업무-계약)을 따른다. 접근성 설정 화면·저장 방식은 F-04의 프론트 로컬 범위를 유지한다.

### 2.3 인증 저장소와 검수 기준

관계형 데이터는 MariaDB 11.8.9, 인증 토큰 상태는 Redis Open Source 8.2.9를 사용한다. 토큰 전용 RDB 테이블은 없다. learning_sessions.assigned_problems의 JSON과 기존 학습 저장 구조는 유지한다. JWT 원문 보관은 클라이언트, 서명 검증·Redis 상태 검증과 폐기는 백엔드의 책임이다. 상세 저장소·버전 근거는 [ERD V2](./erd.md#physical-rules)를 따른다.

동시 action 제출은 한 번만 성공하고 Refresh 회전·재사용 탐지·현재 Redis family 폐기와 auth_version 기반 사용자 인증 세션 전체 무효화가 동작해야 한다. 토큰 종류를 바꿔 다른 API에 넣기, 만료·폐기 토큰과 Redis 상태 누락을 통한 우회를 거부한다. 이전 토큰의 재사용 탐지에 필요한 상태를 조기에 삭제하지 않는다.

MariaDB 변경과 Redis 폐기를 하나의 SQL 트랜잭션이라고 설명하지 않는다. 저장소 일부 실패·재시작·복원·동시 로그인에서 폐기된 인증이 살아나지 않아야 한다. 구체 복구 순서와 장애 HTTP/code는 [API V2 3.6.2절](./api-spec.md#362-인증-저장소-장애와-부분-성공-계약)을, 화면 안내는 [API V2 3.7절](./api-spec.md#37-메일-요청완료-api-클라이언트-복구)을 따른다.

개인 학습·복습은 서버의 한 세션에 배정 문항 참조를 저장하고 실제 풀이·평가와 연결한다. 별도 배정 테이블 없이도 소유권·순번·문제·단계 일치·멱등 제출·완료 여부를 백엔드에서 검증한다. 중단 후에는 같은 세션의 확정된 배정과 결과를 복원한다. 저장 정의는 [ERD의 학습 세션](./erd.md#table-learning_sessions), 요청·응답은 아래 개인 학습 API 계약을 따른다.

### 3.1 개인 학습 세션 API·화면 상태

개인 학습·복습은 별도 유형 없이 같은 흐름과 `FREE` 풀이 mode를 쓴다. 세션 생성, current 조회, sessionId 상세, itemNo 답안 제출, 분석 적용, 결과 조회의 6개 API를 사용한다. 별도 이어하기·완료 버튼용 API는 두지 않는다. 마지막 정상 답안 저장 시 자동 완료되고 프론트가 분석 API를 호출한다.

화면은 서버가 파생한 `IN_PROGRESS | ANALYSIS_PENDING | ANALYZED`를 기준으로 전환한다. 분석 대기 중 앱이 종료되면 current 조회 후 분석을 재시도하고, 이미 분석된 세션은 기존 결과만 반환한다. `PERSONALIZED | MIXED | DEFAULT`도 배정 결과에서 파생해 안내 용도로 사용하며 클라이언트가 지정하지 않는다.

제출은 sessionId·itemNo와 UUID v4 `Idempotency-Key`, cells, NULL 가능한 durationMs만 보낸다. 사용자·문제·단계·mode·정답·점수는 서버가 결정한다. 미제출 문제에는 정답 정보를 노출하지 않고 제출된 문제의 결과만 보여 준다. 현재 상태 조회는 세션 요약과 현재 user_skill_memory를 구분하며 과거 숙련도 Snapshot으로 표시하지 않는다. 완료 기록과 소유자가 알고 있는 sessionId의 상세·결과 조회는 유지하되 완료 세션 목록·기간 통계·숙련도 변화 그래프는 MVP에서 제공하지 않는다.

### 3.2 안내·반복·피드백 세부

풀이 전에는 조작 방법·목표를 안내하고 현재 미제출 문항의 정답 점형은 숨긴다. 정상 독립 풀이를 저장한 뒤 정답·차이를 공개하고 음성·햅틱·아두이노 안내와 따라 하기를 제공한다. 따라 하기는 서버 풀이·10문항·BKT에서 제외한다. 현재 풀이에서 정답 안내 없이 스스로 답하는 과정은 독립 풀이이며 앞서 배운 사실 자체로 제외하지 않는다.

학습 내용 하나는 문제 하나(problem_id)다. 첫 번째 5문항에는 서로 다른 문제 5개를 한 번씩, 두 번째 5문항에는 바로 그 5개를 순서를 섞어 각 한 번씩 다시 배정한다. 각 문제는 정확히 두 번 등장하고 같은 문제를 연속 배정하지 않는다. 제출 후 정오답·설명을 제공하되 따라 하기로 최초 오답을 정답으로 덮어쓰지 않는다. 오답 때문에 세션 문항 수를 자동 증가시키지 않는다.

설명·촉지·피드백 포함 총시간과 피로도를 테스트해 학습량이 많으면 줄인다. 두 번 정답만으로 완전 숙달로 판정하지 않는다. 문제 5개는 problem_id 5개를 뜻하지만 각 문제는 여러 학습 요소와 연결될 수 있으므로 학습 요소 5개와 같다는 뜻은 아니다.

### 4.1 단계 기본 문제·추천·진급 세부

`curriculum_problems.default_order_no INT NULL` 하나를 추가한다. 값이 있으면 해당 단계의 기본 문제와 기본 순서를 뜻하고 1 이상이어야 하며 `(curriculum_stage_id, default_order_no)`는 고유하다. 별도 `is_default` 컬럼·기본 문제 테이블·단계-요소 테이블은 만들지 않는다. SYSTEM Seed는 단계별 5개씩 총 최소 30개의 서로 다른 문제로 구성하고 각 기본 문제를 하나의 기본 단계와 순번 1~5에 연결한다.

개인화 후보는 현재 단계의 유효 문제에서만 고른다. 각 문제에 연결된 요소 중 가장 긴급한 하나를 기준으로 취약(0.70 미만, 낮은 확률 우선) → 미관측 기본 문제(default_order_no 순) → 학습 중(0.70 이상 0.95 미만) → 숙련 순으로 정렬한다. 동률은 한 번도 풀지 않았거나 더 오래된 문제를 먼저, 그다음 problem_id 순으로 결정한다. 주·보조 요소와 별도 추천 가중치는 두지 않는다.

assigned_problems에는 item_no와 problem_id만 두며 기본/개인화 여부·추천 사유를 저장하지 않는다. DB 오류 또는 기본 문제까지 사용해도 현재 단계의 서로 다른 유효 문제 5개를 얻지 못하면 콘텐츠 준비 부족으로 세션을 만들지 않는다. 다른 단계·미검증 문제·세 번째 중복·부분 세션으로 대체하지 않는다. 내부/외부 오류 경계는 내부 서비스 계약, 지연은 기준으로 먼저 측정하고 후속 목표를 정한다.

### 4.2 문제 등록·문제은행 공개 기능

- 공개 문제 등록·은행/상세·학습 요소 목록은 INSTRUCTOR만 사용한다. 단계 목록은 LEARNER·INSTRUCTOR가 사용하며 ADMIN 권한은 자동 부여하지 않는다. LEARNER는 세션·수업 문맥으로만 문제를 받는다.
- 공개 등록은 problemType·trim/NFC한 targetText·cells·중복 없는 skillIds·curriculumStageIds만 받는다. sourceType·creatorUserId는 서버가 INSTRUCTOR·현재 강사로 결정한다. SYSTEM 기본 문제는 Seed, AI 문제는 후속 내부 서비스 계약으로 구분한다.
- 공개 등록 문제는 L1~L6 중 한 단계 이상과 연결한다. L0·L7·L8 및 단계가 없는 LIVE 전용 문제는 MVP에서 등록하지 않는다. 모든 요소는 규칙 엔진이 독립 평가할 수 있어야 한다.
- 문제·Cell·요소·단계 연결은 전체 검증 뒤 한 트랜잭션으로 저장한다. 검증 규칙 위반은 422, 검증 시스템 장애는 503이며 모두 일부 저장 없이 종료한다.
- 문제은행은 단계·요소·문제 유형·출처의 단일 값 AND 필터, page 0·size 20 기본/최대 100, createdAt asc/desc와 problemId 보조 정렬을 제공한다. 자유 텍스트·다중 OR 필터는 제외한다.
- 목록에는 정답 Cell을 넣지 않고 INSTRUCTOR 상세·등록 성공에만 expectedPattern을 포함한다. LEARNER의 정답 공개는 문제·Cell 채점 규칙을 유지한다.
- 문제는 불변이므로 UUID v4 `Idempotency-Key`와 problems.creation_idempotency_key를 사용해 같은 강사의 네트워크 재전송 중복을 방지한다. 같은 키·같은 정규화 요청은 기존 결과, 같은 키·다른 요청은 충돌이다. 의미상 유사 문제 자동 중복 판정은 하지 않는다.
- 공개 endpoint 5개와 DTO·권한·오류 전문은 [API 명세 V2 5절](./api-spec.md#5-문제-등록조회-업무-계약)을 따른다. 문제 수정·삭제·수업 후 재등록·학습 요소 공개 쓰기 API는 없다.

### 4.3 SYSTEM Seed·AI 내부 문제 기능

- SYSTEM 기본 문제는 버전 관리 파일과 일회성 마이그레이션으로 등록한다. 공개·내부 Seed HTTP API와 Seed 전용 DB 구조는 만들지 않는다.
- Seed 버전은 L1~L6 단계별 5개씩 총 최소 30개의 서로 다른 SYSTEM 문제를 하나의 기본 단계·순번 1~5와 연결한다. 문제·Cell·요소·단계·순서를 모두 검증한 후 저장하며 하나라도 실패하면 해당 버전 전체를 롤백한다. 중복 실행은 마이그레이션 이력으로 막는다.
- AI 후보 생성은 AI 서비스의 `POST /api/v1/problem-candidates`, 문제 내용 검증은 `POST /api/v1/problem-validations`로 구분한다. 외부 호스트 Nginx의 사용자 `/api/`에 연결하지 않고 Backend만 내부 네트워크와 필수 `X-Internal-Api-Key`로 호출한다. 키는 Secret으로 주입하며 로그·응답·DB에 남기지 않는다.
- 후보 생성 조건은 `X-Request-Id`, 확인된 L1~L6 단계, 하나 이상 요소 코드·유형, 허용 문제 유형, count 1~5다. body requestId는 사용하지 않으며 AI 응답의 단계·요소 식별값은 최종 연결 권한으로 사용하지 않는다.
- AI 서비스는 DB에 접근하거나 문제 ID·출처·작성자·시각을 정하지 않는다. Backend가 최종 확인한 문제만 AI 출처·작성자/공개 멱등 키/기본 순번 NULL로 네 관련 테이블에 원자 저장한다.
- 학습 세션 생성 중 AI를 동기 호출하지 않는다. 후보 없음은 200·빈 candidates, 검증 부적합은 200·valid=false/violations인 정상 결과다. 실제 내부 인증/입력/장애/시간 초과는 401/422/503/504로 구분한다. 사전 보충 실패·빈 후보는 저장하지 않고 SYSTEM 문제로 fallback하며 내부 오류를 학습자에게 직접 노출하지 않는다.
- 규칙 채점·오답 귀속·BKT·추천·SYSTEM fallback은 MVP 필수이고 AI 생성/검증은 보조 Should다. 모델·제공자·프롬프트·자동 생성 주기·재고·재시도·통과율은 AI 구현 시작 때 별도 확정한다. 모델/프롬프트 메타데이터의 DB 저장은 MVP에서 제외한다. AI 성공률은 MVP 완료 조건이 아니다.

DB 고유 제약은 응답 캐시 만료 후에도 유지한다. 멱등 키의 위치와 오류 코드는 API 계약을 따른다. 개인화는 다음 학습에 반영하며 현재 세션을 문제마다 재구성하지 않는다. 진급 판정은 열린 최고 단계 세션 분석 때 기본 문제 전체의 연결 요소 상태로 수행하고 미관측 요소는 진급을 막는다. HLR·SRS는 MVP에서 계산하지 않고 estimated_half_life·next_review_at은 NULL로 유지한다. 카운터 비율이나 EMA를 BKT로 대체하지 않는다.

### 5.1 요소별 평가·BKT_V1 세부

- 모든 저장·출제 문제는 최소 한 개의 problem_skills 연결과 연결 요소별 독립 평가 규칙을 갖는다. 유효한 독립 풀이 한 건에는 연결된 모든 요소의 attempt_skill_results가 정확히 한 건씩 필요하고, (attempt_id, skill_id)는 고유하다. 누락·초과·중복·판정 실패 시 Attempt·Cell·요소 결과를 전부 롤백한다.
- is_correct=true와 error_count=0, is_correct=false와 error_count>=1은 서로 동치다. 오류는 명시 규칙으로만 요소에 귀속하고 문제 전체 오답을 모든 요소에 복사하지 않는다. error_count는 진단 정보이며 BKT 가중치가 아니다.
- BKT_V1은 P(L0)=0.20, P(T)=0.10, P(G)=0.20, P(S)=0.10이며 이진 is_correct만 사용한다. 정답 posterior는 p×(1-S)/[p×(1-S)+(1-p)×G], 오답 posterior는 p×S/[p×S+(1-p)×(1-G)]이고 p_next=posterior+(1-posterior)×T를 저장한다.
- 첫 유효 관측 때 사용자·요소 상태 행을 생성하고 행 없음은 미관측으로 해석한다. 동일 요소의 여러 관측은 session_item_no 순서로 모두 적용한다. 처음 두 번 연속 정답은 약 0.874이므로 숙련 임계값 0.95에 미달한다.
- mastery_probability는 0~1의 DECIMAL(7,6), algorithm_version은 백엔드의 BKT_V1이다. 파라미터를 프론트나 요청에서 받지 않는다. total_seen=total_correct+total_incorrect를 유지하고 관측마다 seen과 정답/오답 중 하나만 증가시킨다.
- last_practiced_at은 마지막 유효 개인 FREE 풀이 시각, updated_at은 분석 성공 시각이다. 상태·카운터·시각·analysis_applied_at은 원자적으로 반영한다. LIVE 결과는 이를 직접 갱신하지 않는다. 버전 변경 시 기존 상태 이행 방식은 후속 승인 대상이다.

### 6.1 실시간 수업 운영·전송 세부

- 수업 생성 시 서버가 앞자리 0을 허용하는 숫자 6자리 participation_code를 발급한다. 값은 전체 고유하며 재발급·재사용하지 않는다.
- SCHEDULED에서 제목·설명·예정 시각을 수정하고 문제를 연결·해제할 수 있다. OPEN에서는 새 문제 연결과 현재 문제 전달만 가능하며 기존 연결 삭제는 금지한다. CLOSED에서는 변경·입장·전달·신규 풀이를 금지한다.
- 현재 문제는 current_lecture_problem_id로 보존하여 재접속 조회의 기준으로 사용한다. 하나의 현재 문제를 활성 참여자 전체에 전달하며 개별 학습자 대상 출제는 MVP에서 제외한다.
- 참여자는 최초 입장 시각을 유지하고 직접 퇴장 시각만 갱신한다. 재입장은 기존 행의 left_at을 NULL로 되돌리고 수업 종료 시 접속 중 참여자의 left_at을 종료 시각으로 기록한다. 체류 시간과 출결 결과는 계산하지 않는다.
- LIVE는 OPEN·현재 문제·활성 참여자를 서버가 검증하고 curriculum_stage_id와 개인 세션 연결은 NULL로 저장한다. 같은 수업·학습자·문제에는 최종 풀이 한 건만 허용한다.
- 종료와 제출은 lectures 행 잠금 순서로 직렬화한다. 먼저 OPEN을 잠근 유효 제출은 저장 후 종료하고, 먼저 CLOSED가 된 뒤의 신규 제출은 거부한다. 저장된 동일 멱등 요청은 기존 결과를 반환한다.
- 수업 생성/조회/수정/상태 전이, 코드 참여/퇴장, 문제 연결/해제/현재 문제 지정, LIVE 답안은 `/api/v1` HTTP API로만 저장한다. 수업 목록은 담당 강사 본인 자료를 page/size로 조회하며 기본 size 20·최대 100이다.
- WebSocket은 메타데이터·상태·현재 문제 변경 알림만 서버에서 전달한다. Access JWT로 60초 유효 일회용 티켓을 발급받아 연결하고 답안·채점 결과·다른 참여자 정보는 방송하지 않는다.
- 연결이 끊기면 새 티켓과 `GET /api/v1/lectures/{lectureId}` Snapshot으로 현재 상태를 복구한다. 이벤트 이력·sequence·replay cursor와 새 DB 컬럼은 두지 않는다.
- 수업 종료 후 학습자가 복습을 선택하면 강의 상세의 `reviewableCurriculumStages`에서 열린 단계별 본인 오답 수를 확인하고 하나의 단계를 선택한다. 후보가 5개보다 적으면 기존 BKT 추천과 SYSTEM 기본 문제로 보충하고, 5개를 초과하면 실제 오답 요소의 상태·개인 FREE 풀이 이력·problemId 순으로 상위 5개를 선정해 일반 FREE 10문항 세션을 구성한다. 자동 세션 생성·기존 세션 덮어쓰기·문제 ID 클라이언트 입력·별도 REVIEW mode는 사용하지 않는다.
- OpenVidu 상세 계약은 다음 스프린트로 이월하고 참여자별 상세 실시간 대시보드는 MVP에서 제외한다. LIVE의 직접 BKT 반영 여부는 수업 후 복습 규칙으로 해소했다.

## 9. 기능 수용 검증

1. 같은 계정이 동시에 여러 역할을 갖지 않으며 타인 결과를 멱등 키로 조회할 수 없다.
2. 자가 진단의 여섯 분기·모두 안다·L0 건너뛰기가 정의대로 동작하고 개별 응답·숙련 기록을 만들지 않으며 users.level에는 열린 최고 단계만 남긴다.
3. 짧은 안내와 독립 풀이 10문항이 구분되고, 서로 다른 문제 5개가 각각 정확히 두 번·연속 중복 없이 배정된다.
4. 제출 전 정답이 숨겨지고 저장 후 정답·차이가 공개되며, 프론트 안내·따라 하기가 최초 오답을 덮어쓰거나 서버 풀이·현재 세션 문항 수를 늘리지 않는다.
5. 중단·재개·결과 재조회·네트워크 재전송으로 학습 상태가 중복 갱신되지 않는다.
6. 검증 실패 문제·관련 일부 행은 남지 않고, 모든 문제는 최소 한 개의 독립 평가 가능한 요소를 가지며 L1~L6 단계별 SYSTEM 기본 문제 5개씩·전체 최소 30개를 제약으로 실제 조회·구성할 수 있다.
7. 장치 없이 학습이 지속되고 출력 실패·인터넷 실패가 서로 구분된다.
8. 사전 입장이 수업 시작으로 처리되지 않으며 종료 후 신규 LIVE 제출만 차단한다. 같은 수업 상태·문제 연결·참여/퇴장·답안 재요청은 멱등 결과를 따르고 상태 역행·현재 문제가 아닌 제출은 거부한다.
9. 음성은 전달만 하고 저장하지 않으며 BKT는 완료한 개인 학습의 요소별 이진 관측에만 반영한다. 처음 두 번 연속 정답은 숙련으로 판정하지 않고 카운터·시각·분석 반영도 원자적으로 갱신한다.
10. 추천 부족·오류·시간 초과는 승인된 기본 문제 fallback으로 완전한 10문항만 만들고, 기본 문제까지 부족하면 세션을 생성하지 않는다.
11. 열린 최고 단계의 진급 조건은 기본 문제 전체 연결 요소 0.95 이상이며 미관측·하위 복습·L6에서는 진급하지 않는다.
12. 설명·촉지·피드백을 포함한 총시간과 피로도를 측정한다. 테스트 모집 인원과 합격 수치는 실제 대상·환경을 확정한 뒤 승인한다.

비분리 구조는 타인 세션 접근·잘못된 배정/풀이 연결·배정 위치 중복·동시 제출/완료·재전송·중단 후 복원 사례로 검수한다. 백엔드의 사전 검사만으로 동시성 안전성을 통과 처리하지 않는다. 실제 연결 필드는 풀이 연결 제약, 완료 조건·원자적 처리 방식은 세션 생명주기 규칙을 따른다.

현재는 문서상 검수 기준이며 구현·테스트 완료를 의미하지 않는다. 비기능 요구와 성능 측정은 12~14절, 문서 검수 순서는 15절을 함께 확인한다.

### 10.1 접근성

Android의 TalkBack 핵심 흐름, 조작 요소의 이름·역할·상태, 6점 입력과 탐색 충돌, 200% 글자 확대, 색상에만 의존하지 않는 상태 표시를 실기기로 검증한다. 자동 검사만으로 촉지 학습의 사용성을 판정하지 않는다. WCAG 전체 적합 선언이나 기기별 목표값은 별도 시험을 거쳐야 한다.

### 10.2 성능·신뢰성

하나의 실제 수업에 최대 30명이 참여해 같은 문제를 동시에 제출하는 시나리오를 사용한다. 성공 응답의 DB 누락, 최종 풀이·BKT 중복, 미검증 문제 제공, 타인 리소스 접근은 허용하지 않는다. 수업 재접속 후 HTTP Snapshot으로 현재 상태가 복구되어야 한다.

채점 응답·세션 생성·WebSocket 전파의 p95와 환경·데이터량·동시 사용자 조건을 함께 기록한다. 20개 수업·600명, 300/500/800ms, 월 99.5% 등의 과거 수치는 현행 합격 기준이 아니다. 실제 기준선 측정 후 목표를 확정한다. 설명·촉지·피드백을 포함한 학습 총시간·피로도도 측정하며 모집 인원은 실제 대상·환경을 확보한 뒤 기록한다.

### 10.3 운영·유지보수·콘텐츠

환경별 설정과 비밀값을 분리하고 비밀번호·토큰·내부 키·직접 식별정보가 로그에 노출되지 않게 한다. 요청 ID 로그·health check·마이그레이션/롤백 검증은 필수다. 실제 사용자 데이터 수집 전 영속 DB, 백업 절차, 별도 환경에서 최소 한 번의 복원 시험을 마련한다. 법적 보존 기간·자동 파기·백업 제거 시점·RPO/RTO는 운영 정책으로 확정한다.

파트별 구조·코드 규칙을 따르고 채점·권한·멱등·경계값과 변경 회귀를 검증한다. 전 파트 동일 구조 강제·커버리지 90%·특정 관측 도구 도입은 별도 결정 대상이다. BKT 설정은 백엔드에서 버전 관리하며 버전 변경 시 기존 상태 이행을 검토한다. 모델·프롬프트·추천 이력의 추가 DB 저장은 MVP에 포함하지 않는다.

말뭉치·문제 콘텐츠·학습 기록의 출처·이용 조건·수집 목적·동의 범위를 검수한다. 라이브러리·폰트·외부 도구의 라이선스와 실제 지원 점역 규칙을 확인하고, 검증되지 않은 자료를 자동 도입하지 않는다.

## 11. 문서 연결과 후속 계약

기능 번호 F-01~F-26은 기능 식별자이며 API 명세의 A 번호와 연결한다. 데이터 저장·FK·컬럼 역할은 [ERD](./erd.md), 화면 전환·오류 복구는 [사용자 Flow](./user-flow.md), 교육 단계·진급은 [커리큘럼](./curriculum.md)을 따른다.

실제 SYSTEM 콘텐츠, 최소 지원 Android·BLE 통신 상수, OpenVidu 연동 세부, 측정 후 성능 목표·운영 보존 값은 후속 산출물이다. 응답 필드 등 문서 검수 중 발견된 미확정 사항은 정리 검수 보고서(로컬 별도 참고 자료)에서 추적한다. 이전 개발계획서의 비교표·수치와 변경 전 본문은 정리 전 보존 자료에 남긴다.
